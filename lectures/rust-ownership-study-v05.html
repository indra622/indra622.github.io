소유권과 이동

Rust는 왜 "이 값의 주인이 누구인가"를
코드에 드러나게 관리할까?

진행 (1분)

인사하고 오늘의 질문 하나를 크게 읽습니다. "Python에서는 누가 메모리를 치우는지 신경 쓴 적이 거의 없죠. Rust는 그걸 코드에 드러냅니다. 왜 그럴까요?"

표지 그림 (v04)

힙의 "hello" 버퍼는 제자리에 있고, 주인 열쇠만 s1에서 s2로 옮겨 갑니다. s1은 이동되어 쓸 수 없고, clone은 새 버퍼(할당 #2)를 따로 만듭니다. 오늘 배울 이동과 복제를 한 장으로 미리 보여 주는 그림입니다.

안내

  • 화면의 실행 결과는 모두 미리 계산한 결과입니다. 브라우저가 Rust나 Python을 실행하지 않습니다.
  • 예제 코드는 실제 rustc 1.96.1, Python 3.14.6에서 확인했습니다.

오늘의 길

메모리 지도에서 시작해 소유권 규칙까지

목표 1소유권 규칙 3가지를 내 말로 설명한다
목표 2String, Vec에서 이동이 일어나는 줄을 짚는다
목표 3Move, Copy, Clone 차이를 예제로 보인다
목표 4Python의 참조와 GC를 Rust의 자원 관리와 비교한다

지도의 원을 누르면 그 단원으로 갑니다. I를 누르면 전체 목차, ?는 단축키 안내.

진행 (2분)

A부터 G까지 일곱 구간을 길을 따라 짧게 소개합니다(위 줄 왼쪽에서 오른쪽, 다시 아래 줄 오른쪽에서 왼쪽). 길 끝의 깃발이 아래 목표 네 개를 가리킵니다. 목표를 소리 내 읽습니다.

질문

  • "Python에서 a = b 를 쓰면 무슨 일이 일어난다고 생각하나요?" 답을 받아 두고 13번 화면에서 다시 꺼냅니다.

지난 시간 복습

지난 시간에 본 낱말, 다시 짚고 시작해요

변수 variable

값에 붙이는 이름. Rust는 "바인딩"이라고도 함.

진행 (3분)

지난 시간에 다룬 낱말 여섯 개를 빠르게 되짚습니다. "기억나는 뜻을 먼저 말해 보세요"로 시작하고, 시뮬레이터를 한 단계씩 넘기며 확인합니다. 단계마다 관련 카드가 노랗게 켜집니다.

마지막 두 단계 (v03)

  • 5단계: 스코프가 끝나 x, y 이름을 더 쓸 수 없습니다. 흐린 칸은 설명용 흔적입니다.
  • 6단계: main 프레임이 스택에서 빠지고 TOS가 바닥으로 내려갑니다. 그 칸은 "다시 쓸 수 있는 자리"가 될 뿐, 값을 0으로 지우거나 운영체제에 메모리를 돌려주는 것이 아닙니다. 그림은 교육용 모델이며 실제 스택 덤프가 아닙니다.

설명

  • Rust의 let은 "이름을 값에 묶는다(바인딩)". 기본은 바꿀 수 없음.
  • 주소와 객체는 다음 화면들에서 쓰입니다. 주소는 String의 ptr 칸, 객체는 Python 그림에서 나옵니다.

질문

  • "4번 줄에서 mut를 지우면 어떻게 될까요?" (컴파일 오류. 22번 화면 Q6에서 다시 봅니다.)

B 메모리 기초

스택은 접시 쌓기와 닮았어요

규칙 하나: 맨 위에만 올리고(push) 맨 위에서만 꺼낸다(pop).

나중에 올린 것이 먼저 나갑니다. 이것을 LIFO(Last In, First Out)라고 부릅니다.

비유는 비유일 뿐입니다. 진짜 스택에는 접시 대신 함수 호출마다 프레임(그 함수가 쓰는 칸 묶음)이 쌓입니다. 다음 화면에서 봅니다.

진행 (2분)

단계를 넘기며 "다음에 나올 접시는?"을 물어봅니다. pop D, pop B 단계 직전에 예측하게 합니다.

방향

  • 접시는 위로 쌓이고 "맨 위(top)"도 위에 있습니다. 3번과 5번 화면 이후의 스택 그림도 같은 방향(새것이 위)입니다.

주의

  • 비유를 오래 끌지 않습니다. 핵심은 "맨 위에서만 넣고 뺀다", 그래서 빠르고 정리가 쉽다.

진짜 스택: 함수를 부를 때마다 프레임이 쌓여요

새 프레임은 위에 쌓이고, 함수가 끝나면 통째로 빠집니다. 그림은 위가 낮은 주소인 교육용 배치이며 실제 변수 위치를 보여 주지 않습니다.

진행 (3분)

3단계(add 호출)에서 멈추고 접시 그림과 비교합니다. "맨 위 프레임이 add죠? add가 끝나면 어디가 빠질까요?"

설명

  • 프레임: 함수 한 번 호출이 쓰는 칸 묶음(매개변수, 지역 변수).
  • i32는 Copy라서 a, b 값이 p, q로 복사됩니다(17번 화면에서 자세히).

그림의 방향 (v02)

  • 모든 Rust 메모리 그림은 같은 약속을 씁니다: 위쪽이 낮은 주소, 아래쪽이 높은 주소. main 프레임이 맨 아래, 새 프레임과 새 칸은 그 위에 쌓입니다. 점선 TOS(스택 꼭대기) 표시가 지금 가장 위를 가리킵니다. 4번 화면 접시와 같은 방향입니다.
  • 많은 기계(x86-64, AArch64 등)에서 스택은 낮은 주소 쪽으로 자랍니다. 그래서 낮은 주소를 위에 두면 "위로 쌓인다"가 됩니다. 다만 아키텍처, ABI, 컴파일러에 따라 다르고, 지역 변수는 레지스터에만 있거나 순서가 바뀌거나 아예 사라질 수 있습니다.
  • 따라서 그림의 칸 순서와 위치는 실제 오프셋이 아닙니다. "교육용 배치이지 메모리 덤프가 아니다"라고 한 번 말해 줍니다.

주의

  • "Rust 변수는 모두 스택에 있다"고 말하지 않습니다. 오늘 그림은 교육용 모델이고, 최적화로 실제 배치는 달라질 수 있습니다.

힙: 크기가 변하는 String은 버퍼를 따로 잡아요

  1. let literal = "hi"; (2번 줄) literal은 &'static str. 이미 고정 데이터에 있는 바이트를 가리킬 뿐, 힙 할당이 없습니다.
  2. String::from(literal) (3번 줄) 힙에 새 버퍼를 잡고 바이트를 복사합니다. s가 그 버퍼의 주인입니다.
  3. literal이 가리키는 곳은 SSD가 아니라 실행 중인 프로세스의 메모리입니다. 모든 &str가 고정 데이터를 가리키는 것은 아니고, String 안의 바이트를 가리킬 수도 있습니다.

진행 (3분)

시작 화면은 비어 있습니다. 1단계에서 &str 리터럴은 힙이 아니라는 점을 짚고, 2단계에서 String::from이 힙을 새로 잡는 것을 보여 줍니다.

1단계에서 "hi"가 나타나는 이유 (v03)

  • "hi" 바이트는 컴파일할 때 프로그램 파일의 읽기 전용 데이터에 들어가므로, 이 줄이 실행되기 전부터 이미 있습니다. 1단계에서 그림에 처음 비추는 것은 설명을 위한 연출입니다. let이 바이트를 새로 만들거나 힙에 잡는 것이 아닙니다.
  • (v05) 저장된 파일과 실행 중 메모리를 구분합니다. SSD의 실행 파일을 실행하면 운영체제가 그 내용을 프로세스의 (가상) 메모리에 올립니다. 스택의 literal은 SSD가 아니라 이 프로세스 메모리의 고정 데이터 영역을 가리킵니다. 그림에서 고정 데이터를 힙과 나란한 별도 영역으로 그린 이유입니다.
  • 언어가 보장하는 것: Rust Reference(literal expressions)에 따르면 문자열 리터럴은 &'static str이고 정적으로 할당된 메모리를 가리킵니다. 그 메모리가 어느 섹션(흔히 ELF의 .rodata, macOS의 __TEXT 아래 섹션)에 놓이는지, 운영체제가 파일 페이지를 언제 실제로 읽어 오는지(필요할 때 페이지 단위로)는 플랫폼과 컴파일러의 세부사항이지 언어 보장이 아닙니다. 깊이 묻지 않으면 넘어갑니다.
  • &str 자체는 "어딘가의 UTF-8 바이트를 빌려 보는 값"입니다. String에서 빌린 &str는 힙을 가리킵니다(다음 시간 빌림).
  • String 칸의 설명표: ptr(힙 버퍼의 주소), len(쓰고 있는 바이트 수), cap(잡아 둔 바이트 수).
  • 마지막 단계에서 s의 힙 버퍼만 해제되고 고정 데이터는 그대로 남습니다(drop 대상이 아님).

설명

  • 문자열 리터럴 "hi"의 타입은 &str입니다. 프로그램 안에 박혀 있는 고정 데이터를 가리킵니다. 힙의 String이 아닙니다.
  • len은 바이트 수입니다. 한글 "안"은 UTF-8에서 3바이트라 len이 3입니다. 오늘 예제는 헷갈리지 않게 ASCII만 씁니다.
  • cap 2에서 8: 7번 화면과 같은 규칙입니다. 새 cap = max(2 × 2, 필요한 4, 1바이트 원소 최소 8) = 8. "항상 두 배"가 아니라 최소값 8이 이긴 경우입니다(rustc 1.96.1).

질문

  • "len과 cap이 왜 따로 있을까요?" (매번 새로 빌리지 않으려고 여유를 둔다.)

진행 (2분)

    
4단계(꽉 참) 다음 5단계에서 버퍼를 키웁니다. 이때 위의 규칙 상자가 노랗게 켜집니다. 규칙을 소리 내 읽고 숫자를 대입합니다: max(4 × 2, 5, 4) = 8.

    
왜 넉넉히 잡나 (v05)

    
  • cap을 1씩 늘리면 push마다 새 버퍼를 잡고 기존 원소를 모두 복사해야 해서 n개를 넣는 데 n²에 가까운 복사가 듭니다. 배수로 키우면 다시 잡는 횟수가 log n 번 정도로 줄고, 복사 총량이 n에 비례해 push 한 번의 평균 비용이 일정해집니다(분할 상환, amortized).
    • 
    
  • "필요한 개수"가 이기는 경우: reserve나 extend로 한 번에 여러 개를 넣을 때. cap 4, len 4에서 6개를 더 넣으면 필요 10 > 8이라 10.
    • 
    
  • "원소 크기별 최소"가 이기는 경우: 작은 Vec. 1바이트 원소(u8, String 버퍼)는 최소 8, 1024바이트 이하 원소는 4, 그보다 크면 1. 6번 화면 String 2 → 8이 이 경우.
    • 
    
  • 그림은 버퍼를 옮긴 경우(#1 → #2)입니다. 할당기는 제자리에서 늘릴 수도 있습니다.

    
cap 숫자의 근거 (질문이 나오면)

    
  • 오른쪽 위 "관찰 근거"를 펼칩니다. examples/rust/r04_vec_capacity_probe.rs를 rustc 1.96.1 (commit 31fca3adb, host aarch64-apple-darwin, Homebrew)로 컴파일해 실행한 출력입니다: push 40까지 cap 4, push 50에서 cap 8.
    • 
    
  • 이 버전 소스 raw_vec/mod.rs의 grow_amortized: cap = max(현재 cap x 2, 필요한 개수), 그리고 원소 크기에 따른 최소값(1바이트 원소 8, 1024바이트 이하 4)과 비교. 실제 키우기는 할당기의 grow(제자리 또는 이동) 또는 allocate.
    • 
    
  • 이것은 구현의 현재 정책이지 언어 보장이 아닙니다. 보장 범위는 Vec 문서 Guarantees 절을 봅니다. 6번 화면 String의 cap 2 → 8도 같은 규칙(1바이트 원소 최소 8)에서 나온 관찰값입니다.

    
설명

    
  • 점선 빈칸은 잡아 두었지만 아직 원소가 없는 자리(spare capacity)입니다.
    • 
    
  • with_capacity(4)는 "적어도 4개" 자리를 보장합니다. 그래서 예제는 cap>=4로 출력합니다.

소유권 규칙 3가지 출처: The Rust Programming Language 4.1장. 단계를 넘기면 해당 규칙이 켜집니다.

  

      
1
값마다 주인(owner)이 있다.Each value has an owner.

      
2
주인은 한 번에 하나뿐이다.There can only be one owner at a time.

      
3

정리: 제약이 주는 안전

  

    
소유권 3규칙
주인은 하나. 주인이 스코프를 벗어나면 drop. 해제는 정확히 한 번.

    
Move
String, Vec 대입과 함수 인자. 설명표만 옮기고 원래 이름은 사용 금지.

    
Copy와 Clone
Copy는 타입이 정하는 자동 복사. Clone은 직접 부르는 복사이고 비용은 타입마다 다름.

    
Python과 비교
Python은 이름을 같은 객체에 묶고 GC가 회수. Rust는 컴파일할 때 주인을 검사.

1. "이동 후 사용 금지"는 불편한 제약일까, 안전장치일까?
실습 1의 Python 코드처럼 두 이름이 한 리스트를 함께 바꾸는 일이 의도였다면? 실수였다면?

      
2. clone()을 아무 데나 쓰면 오류는 사라진다. 그래도 괜찮을까?
18번 화면의 계산기를 떠올려 보세요. 크기와 반복 횟수에 따라 비용이 커집니다. 다음 시간의 빌림이 대안입니다.

      
3. GC가 있는 언어와 비교해 무엇을 얻고 무엇을 내주나?
얻는 것: 해제 시점이 코드에 드러남, 두 번 해제와 해제 후 사용을 컴파일 단계에서 막음. 내주는 것: 처음 배울 때의 낯섦, 컴파일러와 씨름하는 시간.
