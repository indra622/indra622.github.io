2.3 AI교양 제작 흐름 (S21, S27, S28 공통 사례)

이 흐름은 실제 AI교양 제작 세션의 기록을 교육용으로 정리한 것이다. 이번 작업으로 제작을 실행하지 않는다. 최종 확정은 사람이 하는 전환 조건이며, 이 게이트는 그대로 유지한다.

1. 사용자가 원문을 보내면 받은 본문을 v01로 보존하고 정리 노트와 인덱스에 연결한다. 수정본이 오면 새 버전을 만들고 이전 버전은 남긴다.

2. 세션에서 문장과 논지를 다듬고, 필요하면 근거를 확인한다.

3. 사용자가 최종본을 명시적으로 확정한다. 확정 전에는 제작 단계를 열지 않는다.

4. 확정 뒤에는 삽화 한 장을 만들고, 확정 문장과 이미지를 Obsidian에 보존하고, 설정된 광고와 안내 이미지를 넣은 네이버 비공개 초안을 만든다.

5. 초안을 다시 열어 본문, 대표 이미지, 순서, 카테고리를 확인한다. 공개 발행은 이 흐름에 포함되지 않는다.

반복성과 복잡성에 따른 효용: 이 화면의 선택 이유는 한 번의 단순한 일을 무조건 더 많은 역할로 처리하자는 것이 아닙니다. 비슷한 작업을 반복하면 역할 배정, 비교 방식 준비, 검토 기준 확인과 재수정 연결도 반복됩니다. 그 작업이 복잡해 챙길 관계와 검증 지점이 많을수록, 미리 갖춘 분업과 검증 절차를 재사용하는 가치가 커진다는 것이 이 발표의 메시지입니다. 실제 속도나 비용을 측정한 결과나 복잡도에 비례한 성능 보장은 아닙니다. 단발성이고 단순한 작업에서는 순정이 더 가벼울 수 있고, 하네스 자체의 준비와 유지, 조율 비용도 있습니다. 순정에서도 절차와 도구를 잘 갖춰 재사용하면 자기 업무에 맞는 하네스를 만든 셈입니다.

장면: 요청은 '표의 금액 빈칸만 0으로 채워 줘. 번호와 상품은 그대로'입니다. 표에는 세 줄이 있습니다. 번호 0 상품 A 금액 1200, 번호 1 상품 B 금액 빈칸, 번호 2 상품 C 금액 800. 바뀌어야 할 것은 상품 B의 금액 빈칸 하나뿐입니다.

왼쪽, OpenCode 순정의 진행: 같은 요청을 OpenCode 순정으로 하면 네 단계로 진행합니다. 표를 고치고(금액 빈칸에 0), 원본과 비교하고(비교 코드를 짜서), 기준에 따라 검토하고(번호와 상품이 그대로인지), 문제가 있으면 다시 맡깁니다. 호박색 점선은 검토에서 문제가 나오면 처음 단계로 돌아간다는 뜻입니다. 에이전트는 이 네 단계를 모두 할 수 있고, 하위 작업을 맡기거나 만들어 둔 스크립트를 다시 쓸 수도 있습니다. 다른 점은 전용 비교 도구와 검토 연결이 미리 준비돼 있느냐입니다.

화면에서 뺀 각주: v13 화면 아래의 '역할 흐름은 설명용' 각주는 v14에서 화면에서 뺐습니다. 아래 '실제로 실행한 것'과 '설명용인 부분'이 그 경계를 그대로 설명합니다.

역할 흐름 (설명용): 총괄이 요청을 받아 기준(번호와 상품은 그대로, 줄 추가와 삭제 0)을 정하고 작업 담당에게 맡깁니다. 작업 담당이 고친 표를 총괄에게 돌려줍니다. 줄 수는 3 그대로, 빈칸은 0이라 겉보기엔 끝났습니다. 총괄이 검토 담당에게 원본과 결과를 넘겨 비교를 맡깁니다. 검토 담당은 준비된 비교 도구의 결과를 읽고, 금액 빈칸이 0이 된 것은 요청한 변경이지만 상품 A의 번호가 0에서 3으로 바뀐 것은 요청 밖 변경이라고 총괄에게 알립니다. 같은 총괄이 작업 담당에게 다시 고치게 하고(호박색 점선), 고친 표를 다시 검토에 넘깁니다. 화살표 하나가 처음과 다시 확인을 함께 나타냅니다. 검토를 통과하면 그때 총괄이 요청한 사람에게 보고합니다.

OMH를 쓰는 이유: OMH 통합 구성에는 이렇게 역할을 나눠 맡기고 결과를 돌려받는 OMO의 역할 협업과, 원본과 결과를 같은 형식으로 비교하는 도구(data_compare, data_inspect), 필요할 때 쓰는 절차(omh-rigorous)가 한 묶음으로 준비돼 있습니다. 그래서 '요청 밖 변경을 보고 전에 잡는' 검토를 이 일에 바로 붙일 수 있습니다. OMO는 OMH 경계 안에 들어 있습니다. OMH는 도구와 절차를 제공하는 묶음이지 따로 일하는 사람이 아닙니다.

OpenCode 순정과의 차이: OpenCode 순정의 에이전트도 하위 작업을 맡기고, 스크립트로 비교하고, 기준을 프롬프트로 주면 같은 문제를 잡을 수 있습니다. 이미 만들어 둔 스크립트가 있으면 다시 쓸 수도 있습니다. 순정이 못 한다거나 늘 실패한다는 이야기가 아닙니다. 전용 도구가 없다면 비교 코드, 검토 기준, 고칠 것을 되돌리는 연결을 직접 준비해 이어 붙여야 한다는 것이 차이입니다.

실제로 실행한 것: 바뀐 내용은 examples/omh-v12/의 합성 표(CSV 파일)에 OMH 통합 v04 묶음의 data_compare를 번호(id) 기준으로 실제로 실행한 결과입니다. 첫 결과는 원본에만 있는 번호 1개(left_only 1, 번호 0)와 결과에만 있는 번호 1개(right_only 1, 번호 3), 금액이 바뀐 줄 1개(value_changed 1, amount)였습니다. 수정 결과는 left_only 0, right_only 0, 금액 빈칸이 채워진 줄 1개만 바뀌었습니다. 비교 도구는 의도한 금액 변경도 차이로 보고하므로, 기준은 '차이 0'이 아니라 '번호 추가, 삭제 0, 금액만 변경'입니다. 도구 결과의 ok는 호출 성공이라는 뜻이지 기준 통과가 아닙니다.

설명용인 부분: 첫 결과 표는 이 장면을 위해 손으로 만든 합성 데이터입니다. 역할 흐름은 실제 에이전트 실행 기록이 아니며, 모델이 늘 이렇게 판단한다는 뜻도, 자동으로 막는 관문이 있다는 뜻도 아닙니다.

역할 이름: 총괄, 작업 담당, 검토 담당은 교육용 이름입니다. OMH 통합 v04 참고 문서의 역할로 옮기면 총괄은 orchestrator(작업 분해, 역할 배정, 결과 취합과 검증), 작업 담당은 fixer(한정한 수정과 지정한 검사, 재위임 없음), 검토 담당은 oracle(읽기 전용 원인 분석과 리뷰)에 가깝습니다. 이 세 역할 흐름이 늘 고정돼 있다는 뜻은 아니며, 검토 담당이 도구를 직접 실행하는 권한이나 처음부터 끝까지 실제로 돌린 기록을 말하는 것도 아닙니다. 검토 담당은 준비된 비교 결과를 읽는 역할로 그렸습니다. 모든 역할은 고른 같은 모델을 함께 쓰고, 추가 학습은 없습니다. OpenCode와 Python은 미리 설치해야 하는 전제이고 패키지에 들어 있지 않습니다.

말하지 않는 것: 속도나 정확도 수치, 오류가 없다는 보장, 질문 횟수가 늘 준다는 주장은 하지 않습니다. 결과를 받아들일지는 여전히 사람이 결정합니다. 근거는 OMH 통합 v04 참고 문서(구성과 조건, 역할, 도구)이며 로컬 보관 자료로 이 저장소에 들어 있지 않습니다.

장면과 질문 (예시 초안): 새 CSV 파일을 받았다. 열이 무엇인지, 빈 값이 얼마나 있는지 먼저 알아야 한다. 질문: 모델만 더 좋은 것으로 바꾸면 이 일이 해결될까?

핵심 질문: 왜 모델만 바꾸지 않고 작업 틀을 바꾸는가?

한 문장 정의 (사례): OMH는 기존 OpenCode와 OMO 기반 구성을 오프라인 로컬 환경에 맞게 재구성한 사례다. 설정된 모델 하나와 기존 역할 구성을 유지하면서, 과업에 필요한 도구와 스킬, 작업 절차와 검증을 보강했다. OpenCode는 실행 도구, OMO는 기존 역할과 작업 절차를 제공하는 확장이다.

상세 설명 (세 칸): 실제 제약 → 보강한 도구와 작업 절차 → 확인 가능한 증거와 한계

  • 실제 제약: 설치는 로컬 패키지로만 하고, 로컬 파일만 다루며, 모델은 설정된 한 개다.
  • 바꾼 것: 데이터 구조를 행 값 없이 보는 기능, 두 파일을 키 기준으로 비교하는 기능(자동 병합 없음), 설치 없이 환경을 진단하는 기능, 민감 정보를 가린 오류 맥락 기능, 글자 수를 결정론적으로 세는 검증 기능을 더했다. 이 기능들의 세부는 발표자 메모에만 둔다.
  • 재사용한 것: 기존 역할 구성과 설정된 단일 모델을 재사용했다. 도구 실행에는 기존 허용 정책이 적용되며, 읽기 전용이라는 작업 지시만으로 기술적 접근 차단이 생기지는 않는다. 선택형 엄격 절차(omh-rigorous)는 pstack에서 버그 수정, 기능 구현, 근거 기반 조사 절차를 선별해 적응시킨 것이다. 코드 리뷰 절차는 조사 절차를 검토 작업에 맞춰 구성했다. 검증 계획은 기존 OMO 스킬(verification-planning)과 겹치지 않게 조정했다. 원본 흐름 전체를 무조건 따르지 않는다.
  • 확인 가능한 증거와 한계: 설치와 점검 기록, 모의 환경에서의 테스트 결과가 있다. 이 증거는 기능이 연결되었다는 뜻이지 모델 품질을 보장하지 않는다. 실제 사내 모델 품질 비교는 실행하지 않았다.

구체 예시: 장면은 세 단계다. (1) 새 CSV를 받는다. 데이터 구조 점검으로 열, 타입, 빈 값 수, 검사 범위를 보고 행 값은 뺀다. (2) 변경한다. 빈 값 처리 규칙을 적용해 새 파일을 만든다(가상 규칙). (3) 전후를 비교한다. before.csv와 after.csv를 id 기준으로 비교해 추가, 삭제, 변경 행 수를 본다. 입력은 두 파일이고, 출력은 구조 요약과 키 기준 차이 요약이다. 자동 병합은 없다.

헷갈리는 지점:

  • 점검 스크립트가 통과했다고 모델이 더 좋아진 것은 아니다. 스크립트 점검은 기능 연결을 확인할 뿐이다.
  • 모의(mock) 또는 오프라인 검증은 실제 사내 모델의 품질을 증명하지 않는다.
  • 같은 모델의 새 문맥으로 다시 검토해도 독립된 다른 모델의 검토가 되지는 않는다.

화면 구성: 세 칸 가로 배치. 실제 제약 → 바꾼 것 → 확인 가능한 증거와 한계. 가운데 칸에서 재사용한 기반과 우리가 더한 것을 두 색으로 나눈다. 아래 주석: 모델은 재학습하지 않았다.

확인 질문과 모범 답안: 점검 스크립트가 모두 통과했다. 이제 모델이 좋은 답을 낸다고 말해도 될까? 아니다. 통과는 연결과 기능 확인이며, 실제 사내 모델 품질은 따로 측정해야 한다.

Superpowers의 변경 기록(RELEASE-NOTES)은 절차와 검토 방식이 계속 고쳐지고 있음을 보여 줍니다. 그 위의 해석, 곧 '이런 습관이 기본이 될수록 하네스의 가치는 일에 맞춘 검증과 위임으로 옮겨 간다'는 것은 이 발표의 관점입니다. 모든 모델이 Superpowers 문서 자체를 학습했다거나, 모델이 늘 절차를 빠짐없이 따른다거나, 추가 지시가 더는 쓸모없다는 뜻이 아닙니다.

먼저 읽는 위 줄, 실행 기본기: Superpowers에서는 brainstorming이 먼저 의도를 끌어내고 이해한 내용을 되짚습니다. 작은 변경은 대화로, 큰 작업은 설계 문서로 합의합니다. 이어서 작은 단위의 계획을 쓰고, 실행할 때는 작업마다 새 하위 에이전트가 테스트 먼저(RED, GREEN, REFACTOR) 구현하고 작업별 검토 한 번이 명세 충족과 코드 품질을 함께 봅니다. 마지막에 브랜치 전체를 검토하고 마무리 방식을 고릅니다. 하위 에이전트 대신 한 세션에서 실행하고 마지막에 한 번 검토하는 방식(executing-plans)도 있습니다. 위임과 검토도 이미 갖추고 있다는 뜻입니다.

이어서 읽는 아래 줄, 다음 초점: pstack에서는 poteto-mode가 요청을 보고 작업에 맞는 플레이북(README 기준 23개)을 고릅니다. 기능 플레이북을 고르면 영향 범위를 파악하고 설계를 탐색한 뒤, 먼저 끝낼 단계, 독립 작업, 공유 상태, 가장 작은 안전한 분할을 점검하고, 파일 범위와 데이터 구조, 성공 기준을 정해 구현을 맡깁니다. 그다음 돌아온 결과를 실제 동작으로 검증합니다. 코드, 테스트, 실행 결과를 근거와 대조하는 것이며, 화면 캡처만 보는 것이 아닙니다. 플레이북마다 단계는 다르고, 한 기능처럼 코드가 엮인 일은 한 담당자에게 둡니다. pstack에도 계획과 테스트가 있습니다.

제목과 읽는 순서: 제목 '기본기는 모델에, 업무 기준과 위임은 하네스에'가 이 화면의 요지이며, 발표자의 강조점입니다. 그림은 위에서 아래로 읽습니다. 먼저 Superpowers가 잘 다듬어 온 실행 기본기를 보고, 이어서 pstack에서 참고할 다음 초점, 곧 이 일에 맞춘 기준과 근거, 절차 선택, 위임, 검증을 파란색으로 봅니다. 위아래는 설명 순서이지 순위나 전환 단계가 아닙니다. 두 줄을 딱 잘라 나누는 구조도가 아니며, 하네스가 기본기를 신경 쓰지 않아도 된다는 뜻도 아닙니다. 두 묶음은 계획, 위임, 검토, 테스트를 함께 갖추고, 겹치는 부분이 많습니다. 바꿔 쓴다고 정확도나 속도가 저절로 오른다고 말하지 않으며, 잰 수치도 없습니다.

실행 환경: pstack은 Cursor 이름으로 쓰여 있고 Claude Code용 어댑터가 이름을 바꿔 대응하며, Cursor 전용 기능은 건너뜁니다. 호스트마다 똑같이 동작한다고 말하지 않습니다. Superpowers도 여러 코딩 에이전트에 설치 경로를 안내합니다.

표기 주의: Superpowers README의 스킬 목록에는 '두 단계 검토'라는 표현이 남아 있지만, 같은 커밋의 subagent-driven-development 본문은 작업별 검토 한 번이 명세와 품질을 함께 본다고 설명합니다. 이 화면은 스킬 본문을 따랐습니다.

S14. MCP

장면과 질문 (예시 초안): 여러 도구가 파일 목록과 파일 내용을 서로 같은 방식으로 주고받아야 한다. 질문: 도구마다 따로 약속을 만들어야 할까, 공통 약속이 있으면 충분할까?

한 문장 정의: MCP(Model Context Protocol)는 호스트 애플리케이션과 외부 도구 및 자원 서버가 도구 목록 조회, 도구 호출, 자원 읽기를 주고받는 방식을 정한 통신 규약이다.

상세 설명:

  • MCP는 프로토콜이다. 메시지 형식과 교환 절차를 정하며, 그 자체가 특정 도구나 제품은 아니다.
  • MCP 서버는 도구나 자원을 이 규약에 맞춰 노출하고, 호스트는 그 목록을 모델에 제공할 수 있다.
  • 프로토콜이 있다고 인증이 자동으로 되지 않는다. MCP에는 인증 관련 규격도 있지만, 이를 따른다는 사실만으로 접근 권한이 생기지는 않는다. 실제 계정 연결과 허용 범위는 서버와 호스트가 적용한다.

장면에 다시 적용 (예시 초안): 입력: 목록 조회 요청. 출력: 서버가 알려 준 도구 목록과 호출 결과. 공통 약속이 있어도 어떤 폴더를 허용할지는 서버와 호스트 설정이 정한다.

강사용 보충 예시 (화면 생략): CSV를 읽는 MCP 서버가 read_csv 도구를 노출한다. 호스트가 목록을 받아 모델에 보여 주고, 모델이 호출하면 서버가 결과를 돌려준다. 이 설명에서는 MCP 서버 없이 read_file로 같은 일을 한다고 가정한다.

헷갈리는 지점: 도구는 기능이고 MCP는 기능을 주고받는 규칙이다. 모든 도구가 MCP인 것은 아니다. 로컬 함수나 셸 명령은 MCP 없이도 도구가 된다.

화면 구성: 첫 화면은 장면과 질문만 보인다. 답을 공개한 뒤 정의와 적용을 보인다. 호스트 상자(Claude Code 같은 앱)와 MCP 서버 상자 사이에 규약 선을 긋는다. 선 위에 "목록 조회, 도구 호출, 자원 읽기"를 쓰고, 선 아래에 "연결 규약을 따른다는 것과 접근 권한을 얻었다는 것은 다름"이라고 적는다.

확인 질문과 모범 답안: MCP 서버를 연결하면 인증 없이도 모든 데이터를 읽을 수 있는가? 아니다. 인증 관련 규격이 있더라도 실제 계정 연결과 허용 범위를 설정하고 검사해야 한다.
