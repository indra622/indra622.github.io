AI 에이전트에게
일을 맡기는 법

강의 없이 혼자 읽고 따라 할 수 있게 워크숍 내용을 글로 다시 정리했다. Ralphthon과 Ralph 루프가 무엇인지 이해하고, CSV 합계 도구 예제로 루프가 한 바퀴 도는 모습을 본 다음, 실제로 만들어진 사례 4개를 살펴본다. 마지막에는 반나절 동안 혼자 끝낼 수 있는 작은 프로젝트를 고르고 명세를 쓴다.

기준일 2026-11-21. 사실 문장 옆의 작은 표시를 누르면 원문 출처로 이동한다.

이해하기Ralphthon과 Ralph 루프 따라 하기CSV 예제와 루프 데모 사례 보기실제로 만든 것 4개 직접 하기반나절 프로젝트와 템플릿

1이 핸드북으로 얻을 것

목표는 하나다. 이 글을 다 읽고 나면 동작하는 작은 도구 하나를 반나절 안에 직접 만들 수 있어야 한다. 기능이 많을 필요는 없다. 대신 아래 세 가지가 분명해야 한다.

누가 쓰는가

사용자를 한 사람으로 좁힌다. 예: 매달 카드 내역 CSV를 정리하는 나

핵심 기능 하나

오늘 반드시 돌아가야 할 기능. 예: 카테고리별 합계

완료 조건

눈으로 확인할 수 있는 결과. 예: 예시 파일을 넣으면 식비 20,000이 화면에 보인다

이 세 가지가 정해져야 AI에게 일을 넘길 수 있다. 특히 완료 조건이 없으면 AI도 사람도 언제 끝났는지 판단할 수 없다. 이 핸드북의 나머지 내용은 결국 "완료 조건을 어떻게 정하고, AI가 그 조건을 향해 스스로 반복하게 만들고, 언제 멈추게 할 것인가"에 대한 이야기다.

에이전트(coding agent): 파일을 읽고, 코드를 고치고, 테스트 같은 명령을 실행하는 도구를 스스로 골라 쓰는 AI 코딩 도구. Claude Code, Codex CLI, Amp 등이 있다.

2Ralphthon: 에이전트에게 맡기고 손을 떼는 해커톤

Ralphthon은 Team Attention이 운영하는 "에이전트 중심 해커톤"이다. 공식 사이트가 내세우는 원칙 중 하나가 "맡겼으면 손 뗀다"이다. ralphthon.org

서울 첫 행사: 밤새 에이전트가 일하는 형식

첫 행사 RPH-001은 2026년 2월 28일부터 3월 1일까지 서울에서 1박 2일로 열렸다. 토요일 16시에 모여 에이전트 설정과 실습을 하고, 노트북을 넘긴 뒤 사람은 손을 뗀다. 밤새 에이전트가 혼자 일하고, 아침에 결과를 데모하고 시상한 뒤 일요일 11시에 해산했다. 개인 또는 2인 팀으로 9팀 13명이 참가했다. RPH-001 행사 기록

부산 행사: 하루 낮 동안, 규칙도 다르게

모든 Ralphthon이 밤샘인 것은 아니다. 2026년 9월 18일 부산에서 열린 "One-Punch 랄프톤 시즌 2"는 10시부터 17시까지 하루 낮 행사였다. 어떤 에이전트로 루프를 돌려도 되고, 루프 도중에 직접 코드를 고치는 것도 허용했다. 다만 직접 고칠 때마다 '원펀치 스티커'를 붙이게 해서 개입을 최소화하도록 했다. Pathfinder 행사 페이지

정리하면: 밤샘이나 '코드를 절대 안 만진다'는 보편 규칙이 아니다. 행사마다 규칙이 다르다. 공통점은 사람이 손을 떼는 구간을 미리 정하고, 그 구간 동안 에이전트가 스스로 일을 이어 가게 만든다는 점이다. 그 일을 이어 가게 만드는 방법 중 하나가 아래에서 설명할 Ralph 루프다.

3Ralph 루프란 무엇인가

Ralph는 Geoffrey Huntley가 2025년 7월 14일 글에서 소개한 기법이다. 그는 Ralph를 "기법"이라고 부르며, 가장 단순한 형태는 같은 프롬프트 파일을 에이전트에 계속 넣는 셸 반복문 한 줄이라고 설명했다. ghuntley.com, 2025-07-14

while :; do cat PROMPT.md | claude-code ; done

그가 강조한 원칙은 이렇다. 한 번 돌 때 한 가지 일만 한다. 명세(spec)는 파일로 남기고, 할 일 목록 파일에서 가장 중요한 항목을 고르게 한다. 테스트, 타입 검사, 정적 분석으로 잘못된 결과에 제동을 건다. 그리고 이 방법은 기존 코드베이스보다 새 프로젝트에 맞고, 결과를 조율할 엔지니어가 여전히 필요하다고 적었다.

한 번 요청과 계속 도는 루프의 차이

평소처럼 AI에게 요청하면, 모델은 한 턴 안에서 여러 도구를 호출(파일 읽기, 수정, 테스트 실행)한 뒤 답을 하고 멈춘다. 다음에 무엇을 할지는 사람이 결과를 보고 정한다. Ralph 루프에서는 모델이 멈추려 할 때 모델 바깥에 있는 장치가 같은 프롬프트로 다시 시작시킨다. 이 장치는 두 종류로 나뉜다. 셸 반복문은 매번 에이전트 프로세스를 새로 띄우므로 이전 대화가 남지 않는다. 그래서 진행 상황을 계획 파일, 진행 기록 파일, git 커밋에 남겨 두고 새로 시작할 때마다 읽는다. 반면 Stop hook 방식은 같은 세션 안에서 프롬프트를 다시 넣으므로 대화 맥락이 이어지고, 진행 상황은 파일과 git에도 함께 남는다.

상태 파일: 루프가 새로 시작해도 이어서 일할 수 있도록 진행 상황을 적어 두는 파일. 할 일 목록, 진행 기록, git 커밋 이력이 여기에 해당한다.

4루프를 돌리는 방법들

"Ralph"는 특정 제품 이름이 아니라 기법 이름이다. 직접 셸 반복문을 짜도 되고, 공개된 스크립트나 플러그인을 써도 된다. 아래 두 가지는 공개 저장소의 README로 동작 방식을 확인할 수 있는 예다. 어느 쪽을 쓰는 사람이 더 많은지에 대한 자료는 찾지 못했으므로, 둘 다 선택지로만 소개한다.

매번 새 프로세스로 시작: snarktank/ralph

  • ralph.sh가 반복할 때마다 Claude Code나 Amp를 새로 실행한다.
  • 기억은 git 이력, prd.json(할 일과 완료 여부), progress.txt(배운 점 기록)에 남는다.
  • 기본 반복 상한은 10회. 모든 항목이 passes: true가 되면 끝난다.
  • /ralph 스킬은 PRD 문서를 prd.json으로 바꿔 줄 뿐이다. 실제 반복은 셸 스크립트가 맡는다.

snarktank/ralph README

같은 세션 안에서 반복: Anthropic ralph-loop 플러그인

  • 현재 Claude Code 세션 안에서 Stop hook이 종료를 막고 같은 프롬프트를 다시 넣는다. 새 프로세스를 띄우지 않으므로 세션의 대화 맥락이 이어진다.
  • --max-iterations: 기본값은 무제한이고, README는 항상 설정하라고 권한다.
  • --completion-promise: 완료 문구를 정해 둔다. README 예시처럼 모델이 <promise>COMPLETE</promise> 형태로 태그 안에 쓴 문구가 지정한 문자열과 정확히 같을 때 멈춘다. 응답 전체가 같아야 하는 것은 아니다.

ralph-loop README

Stop hook: 에이전트가 응답을 끝내려는 순간 실행되는 사용자 스크립트. ralph-loop는 이 시점에 종료를 막고 프롬프트를 다시 넣는다. 스킬은 에이전트가 참고하는 지침 묶음이며, 그 자체로 반복 실행을 하지는 않는다.

이 핸드북은 설치 방법을 다루지 않는다. 각 도구의 설치와 설정은 위 README를 직접 확인하고, 반나절 실습에서는 이미 쓰고 있는 에이전트로 한 번 요청을 반복하는 방식으로 시작해도 충분하다.

5손을 떼기 전에 사람이 준비할 것

Ralph 루프는 "프롬프트 한 줄 쓰고 자면 끝나는" 방식이 아니다. 사람이 손을 떼는 시간이 길수록 미리 준비해 둘 것이 많다.

  1. 범위와 명세. 한 번에 한 가지 일만 하도록 범위를 좁히고, 무엇을 만들지 파일로 적어 둔다. 대화 속에만 있는 요구 사항은 다음 반복에서 사라진다.
  2. 확인 가능한 결과. 테스트, 타입 검사, 정적 분석처럼 기계가 판단할 수 있는 기준을 둔다. 이것이 잘못된 방향으로 가는 루프를 멈추는 브레이크가 된다.
  3. 격리된 실행. 별도 브랜치나 컨테이너처럼 망가져도 되는 곳에서 돌린다. 에이전트는 명령을 실제로 실행한다.
  4. 예산과 멈춤 조건. 반복 횟수 상한, 비용 상한, 막혔을 때의 기준을 미리 정한다. 이 내용은 8장에서 자세히 다룬다.

6예제 명세: "대시보드 만들어 줘"를 테스트로 바꾸기

"가계부 대시보드 만들어 줘"라는 요청은 AI가 무엇을 만들어도 틀렸다고 말하기 어렵다. 같은 요청을 입력과 기대 결과가 정해진 명세로 바꿔 보자. 아래 CSV는 예제용 가짜 데이터다.

입력: sample.csv

파일 줄 번호데이터 행 번호categoryamount
1헤더categoryamount
21식비12000
32교통3000
43식비8000
54(빈 값)5000

행 번호 규칙: 파일의 첫 줄은 열 이름(헤더)이다. 이 명세에서 "데이터 행 번호"는 헤더를 빼고 1부터 센다. 그래서 파일 5번째 줄이 데이터 4행이다. 이 규칙을 명세에 적어 두지 않으면 AI가 "5행이 무효"라고 답해도 틀렸다고 할 근거가 없다.

기대 결과

  • 카테고리별 합계: 식비 20000, 교통 3000
  • 데이터 4행은 category가 비어 있으므로 무효로 표시한다.
  • 무효 행의 금액 5000은 어느 합계에도 넣지 않는다.

실패 조건과 종료 조건

실패

합계가 위와 다르거나, 데이터 4행의 5000이 합계에 들어가거나, 무효 목록에 4가 없으면 실패다.

종료

테스트 3개(무효 행 제외, 4행 무효 표시, 식비 합계)가 통과하고, 화면에 결과가 보이는 것까지 확인하면 완료를 보고한다.

이 표와 기대 결과를 그대로 AI에게 넘기면 된다. 실제 카드 내역이나 개인정보는 쓰지 않는다.

7루프 한 바퀴 따라가기

위 명세로 루프가 한 바퀴 도는 과정을 단계별로 보여 준다. 실제 AI나 셸을 실행하지 않고, 미리 정해 둔 결과를 재생하는 시뮬레이션이다. 아래 버튼으로 한 단계씩 넘겨 보자.

CSV 합계 도구, 루프 1회시뮬레이션: 미리 정한 결과 재생, AI와 셸을 실행하지 않음
명세구현테스트수정재테스트확인멈춤

  1. 1요청과 명세

    6장의 표와 기대 결과를 그대로 넘긴다. 아직 코드는 없다.

    $ cat spec.md 식비 20000, 교통 3000 데이터 4행: 무효 표시, 합계 제외 (데이터 행은 헤더 제외 1부터)

  2. 2잘못된 첫 구현

    첫 구현은 행마다 category로 묶어 amount를 더한다. 빈 category를 따로 처리하지 않는다.

    // totals.js (v1) for (const row of rows) { totals[row.category] = (totals[row.category] ?? 0) + row.amount }

  3. 3테스트 실패

    테스트가 문제를 잡는다. 빈 카테고리 이름 아래에 5000이 합계로 들어갔고, 4행은 무효로 표시되지 않았다.

    $ npm test FAIL totals excludes invalid rows 기대 { 식비: 20000, 교통: 3000 } 실제 { 식비: 20000, 교통: 3000, "": 5000 } FAIL flags data row 4 기대 invalid: [4] 실제 invalid: [] PASS sums food rows

  4. 4수정

    실패 메시지를 읽고 고친다. category가 비어 있으면 합계에 넣지 않고, 그 데이터 행 번호를 무효 목록에 넣는다.

    // totals.js (v2) for (const row of rows) { if (!row.category) { invalid.push(row.index) // 헤더 제외, 1부터 continue } totals[row.category] = (totals[row.category] ?? 0) + row.amount }

  5. 5재테스트 통과

    테스트 3개가 모두 통과한다. 하지만 테스트 통과가 곧 모든 목표 달성은 아니다. 테스트가 다루지 않는 조건이 남아 있을 수 있다.

    $ npm test PASS totals excludes invalid rows PASS flags data row 4 PASS sums food rows 3 passed

  6. 6완료 기준 확인

    명세의 나머지 조건을 하나씩 확인한다. 화면에 결과가 실제로 보이는지, 가짜 데이터만 썼는지까지 본다.

    ✓ 식비 20000, 교통 3000 ✓ 데이터 4행 무효 표시, 합계에서 제외 ✓ sample.csv는 가짜 데이터 ✓ 브라우저 화면에 결과가 보임

  7. 7멈춤

    완료를 보고하고 멈춘다. 다음 반복을 시작하지 않는다. 이 완료 표지는 모델이 출력한 문자열일 뿐이므로, 사람이 결과를 한 번 더 확인한다.

    <promise>COMPLETE</promise> 루프 종료 (반복 2회, 상한 10회)

8잘 멈추기

루프는 계속 도는 것보다 제때 멈추는 것이 더 중요하다. 멈추는 경우는 세 가지로 나눠 두면 판단하기 쉽다.

완료

테스트 통과와 명세의 나머지 조건 확인이 끝나면 결과를 보고하고 멈춘다.

막힘

같은 오류가 반복되면 멈추고 사람에게 넘긴다. 예를 들어 같은 오류가 3번 나오면 멈추는 식으로 기준을 정해 둔다. 무한히 다시 시도하게 두지 않는다.

예산 상한

반복 횟수나 비용이 정해 둔 한도에 닿으면 멈춘다.

두 가지를 헷갈리지 않아야 한다. 첫째, --max-iterations는 반복 횟수의 상한일 뿐이다. 비용 한도나 계정의 사용량 설정을 대신하지 않는다. 둘째, completion promise는 모델이 <promise> 태그 안에 쓴 완료 문구가 미리 정한 문자열과 같은지만 본다. 테스트 통과와도, 반복 상한과도 다른 장치다. 모델이 "완료"라고 썼다고 해서 결과가 검증된 것은 아니므로, 마지막 확인은 사람이 한다. ralph-loop README

"같은 오류 3번"은 이 핸드북이 예로 든 기준이며, 출처에 나온 규칙은 아니다.

9실제 사례 4개

지금부터는 실제로 만들어진 것들을 본다. 네 사례는 성격이 다르다. 회사의 엔지니어링 프로젝트, 개인이 시작해 재단으로 옮겨 간 오픈소스, 연구 목적의 실험, 돈을 번 개인 게임이다. 그래서 각 사례가 내세우는 숫자도 벤치마크, GitHub 스타, 매출로 종류가 다르고, 서로 순위를 매길 수 없다. 사례마다 AI에게 맡긴 일과 사람이 직접 해결한 일을 나눠서 본다.

Claude C 컴파일러: 에이전트 16개가 2주 동안 만든 컴파일러

AI에게 맡긴 일. 컴파일러 코드 전체. 각 에이전트는 Docker 컨테이너 안에서 돌았고, 공유 git 저장소의 current_tasks/ 폴더에 잠금 파일을 만들어 작업을 나눴다. 지휘하는 에이전트 없이 각자 다음 할 일을 골랐다.

사람이 해결한 일. 테스트 하네스와 검증기, 오픈소스 패키지 빌드 스크립트를 만들었다. 테스트 출력은 모델이 읽기 좋게 짧게 줄이고, 무작위 표본만 도는 --fast 모드를 넣었다. 새 기능이 기존 기능을 자꾸 깨자 더 엄격한 CI를 붙였다. Linux 커널에서 모든 에이전트가 같은 버그에 막히자 GCC를 기준 컴파일러로 섞어 파일 단위로 문제를 쪼갰다.

결과. x86, ARM, RISC-V에서 부팅되는 Linux 6.9을 빌드했고, GCC torture test를 포함한 대부분의 컴파일러 테스트 스위트에서 통과율이 약 99%였다. 한계도 분명하다. Linux를 리얼 모드에서 부팅하는 16비트 x86 단계는 GCC를 호출하고, 자체 어셈블러와 링커는 아직 불안정해 데모에서는 GCC 것을 썼으며, 출력 코드는 최적화를 다 켜도 GCC가 최적화를 끈 결과보다 느리다. GitHub

제품도 사업도 아닌 연구 실험이다. 또 하나의 Ralph 루프가 아니라 에이전트 여러 개가 병렬로 일한 구조라서, 이 핸드북의 CSV 예제와 같은 방식으로 보면 안 된다.

외부 API는 선택이다. 키 발급이나 OAuth 설정에 반나절을 쓰지 않도록 가짜 데이터로 먼저 끝낸다. 에이전트와 루프 도구는 각자 이미 쓰는 환경을 그대로 쓴다. 이 핸드북은 새로 설치하는 것을 전제로 하지 않는다.

아래 칸을 채우면 AI에게 바로 넘길 수 있는 명세 문서가 만들어진다. 비워 둔 칸은 예시 문구로 채워진다. 입력한 내용은 이 페이지 안에서만 쓰이며 저장되거나 전송되지 않는다. 실제 개인정보는 쓰지 말자.

## 프로젝트 명세

### 누구를 위해
매달 카드 내역을 정리하는 나

### 핵심 기능 하나
CSV를 넣으면 카테고리별 합계를 보여 줌

### 완료 조건
sample.csv를 넣으면 식비 20000, 교통 3000, 무효 1행이 보임

### 입력 예시 (가짜 데이터)
category,amount
식비,12000
교통,3000
식비,8000
,5000

### 하지 않을 것
로그인, 서버 저장, 외부 API

### 작업 방식
- 먼저 완료 조건을 확인하는 테스트 2~3개를 만들고, 실패하는 것을 확인한 뒤 구현한다.
- 한 번에 한 가지만 고친다. 고칠 때마다 테스트를 실행한다.
- 같은 오류가 3번 반복되면 멈추고 무엇이 막혔는지 보고한다.
- 테스트가 모두 통과하면 완료 조건을 하나씩 확인하고 결과를 보고한다.
