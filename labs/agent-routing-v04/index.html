에이전트 업무분장과 검증 근거

에이전트별 담당 업무와 시험 결과

Claude Code, Codex, Cursor의 Grok, AGY에 같은 코드 수정과 웹 UI 과제를 맡겼습니다. 네 조합 모두 통과했습니다. 기존 담당은 유지하되, 필요하면 다른 도구에도 작은 작업을 맡길 수 있음을 확인했습니다. 이후 Astra도 같은 과제로 추가 시험했습니다. 아래에 결과를 따로 적었습니다. 이후 어려운 설계 과제도 추가했습니다. 기초 시험과 설계 시험은 아래에서 따로 볼 수 있습니다.

  • 4/4 조합코드 과제. 조합마다 독립 검사 63개 통과
  • 4/4 조합웹 UI 조작. 조합마다 조건 16개 확인 (공통 연결 사용)
  • 1개 / 299개공통 스킬 중 실제로 시험한 수. 4개 조합에서 같은 내용을 읽음

어려운 설계 과제 비교

이번에는 가상의 로컬 스케줄러를 설계했습니다. 실제 OpenClaw 코드를 고치거나 운영 자동화를 실행한 시험은 아닙니다.

SQLite를 두 프로세스가 함께 쓰면서, 전송 직후 장애가 나거나 오래된 워커가 살아나는 상황을 다뤘습니다. 설계서, 실제 SQL, 상태 전이, 장애 사례 8개와 자기 검토를 각각 받았습니다. 아래 비교는 이 과제 하나의 결과입니다.

네 하네스에서 다섯 모델 구성을 시험했습니다. Sol / Astra는 같은 Codex Remote에서 모두 high, Opus도 high였습니다. Grok과 Gemini Flash는 현재 쓸 수 있는 medium 모델입니다. 모델 / 하네스 / 내장 지시는 같지 않으므로, 그 차이를 없앤 순수 모델 성능 비교는 아닙니다.

이번 과제에서 Sol과 Astra는 엄격한 중복 금지를 위한 핵심 구조를 제시했고, 둘 사이의 우열은 확인하지 못했습니다. Opus는 중복 위험을 명시하고 자동 복구 범위를 넓혔습니다. Grok은 이관 뒤 과거 회차 차단을, AGY는 재시도 안전 주장과 일부 SQL을 보완해야 합니다.

과제와 평가 기준

평가 기준 12개와 문제를 실행 전에 고정했습니다. 각 기준은 0~3점입니다. 0은 빠졌거나 위험한 설계, 1은 문제는 알지만 해결 방법이 불완전한 경우, 2는 구체적인 방법에 보완할 점이 남은 경우, 3은 SQL / 전이 / 한계 설명이 맞는 경우입니다. 점수는 AI 검토의 정성 평가이며 검사 통과율이나 일반 성능 점수가 아닙니다. 모델명을 가린 반복 실험도 아닙니다.

  1. 같은 회차 등록과 작업 선점 경합
  2. 멈췄던 워커의 재개와 소유권 변경
  3. 24시간 뒤 만료되는 중복 방지 키와 늦은 요청
  4. 전송 성공 여부를 조회할 수 없는 제공자
  5. 취소 / 수정과 이미 시작된 전송의 경합
  6. 도구 삭제와 인자 계약 변경
  7. 시계의 앞뒤 이동과 재부팅
  8. 과거 원장이 없는 시스템의 이관 / 롤백

제공자 I와 N은 이 시험에서 정한 가상의 API 계약입니다. 실제 서비스의 보장으로 읽으면 안 됩니다.

점수는 이번 설계안에 대한 AI 검토입니다. 모델 전체 성능이나 속도 순위가 아닙니다. 좁은 화면에서는 표를 가로로 넘겨 볼 수 있습니다.

Codex Sol — gpt-6.2-sol / high

불확실한 전송은 반복하지 않는 보수적인 안입니다. Astra와 핵심 안전 결론이 같았습니다.

  • 24시간 키와 도착 지연의 관계를 설명하고, 두 제공자 모두 자동 POST 재전송을 하지 않도록 했습니다.
  • 회차별 일회성 발송 권한과 현재 소유권 확인 조건을 분리했습니다.
  • 검토 에이전트가 중복 등록, lease 경합, 늦은 영수증 / heartbeat 거부, 조회 결과 반영, 취소 후 발송 차단을 SQL로 확인했습니다.
  • 미전송과 전송 성공 후 응답 유실을 구분하지 못하는 경우는 미확정으로 남습니다. 운영자가 새 실행을 승인하면 원래 요청과 중복될 수 있음을 명시했습니다.
Codex Astra — gpt-6.2-astra / high

Sol과 마찬가지로 중복 방지를 우선한 안입니다. 이 과제에서 Sol보다 낫다는 차이는 확인하지 못했습니다.

  • 늦은 원본과 재시도가 24시간 보존 창을 가로지를 수 있음을 설명했습니다.
  • 확정 커밋을 직접 받은 실행 흐름만 일회성 발송 권한을 사용합니다. 재시작 시 DB에서 이 권한을 복원하지 않습니다.
  • 중복 등록, 소유권 인계, 오래된 결과 거부, 취소, 도구 변경의 SQL 전이 검사를 재실행해 통과했습니다.
  • 과거 원장이 없는 작업은 보류하고, 근거가 있는 신규 처리 경계를 승인한 뒤 재개하도록 했습니다. 실제 호스트 / 제공자 검증은 별도로 필요합니다.
Claude Code Opus — claude-opus-5-5 / high

정교한 상태 전이와 SQL 제약을 냈습니다. 제공자 I는 중복 위험을 명시하고 자동 복구 범위를 넓힌 선택입니다. 엄격한 중복 금지와는 정책이 다릅니다.

  • 제공한 메모리 DB 검사를 재실행해 60개 모두 통과했습니다. 다른 후보의 검사 개수와는 직접 비교하지 않았습니다.
  • 오래된 제어 상태 쓰기는 막되, 늦게 도착한 인증된 영수증은 덧붙이는 증거로 분리했습니다. 이 선택 자체는 결함이 아닙니다.
  • 12시간 내 재시도도 늦게 도착하면 중복될 수 있다고 설계서와 자기 검토에서 명시했습니다.
  • 자동 복구를 우선한 이 선택 자체가 오류는 아닙니다. 다만 실제 요구가 엄격한 중복 금지라면 재시도 금지 정책을 추가해야 합니다.
  • 이관의 과거 상태 분류와 신규 처리 경계는 기존 실행기 확인이 필요합니다. 열린 검토 항목을 남긴 채 활성화하는 절차는 보완해야 합니다.
Cursor Agent + Grok — grok-4.7-medium / medium (model variant)

불확실한 요청을 자동 재전송하지 않는 안이며 핵심 SQL 검사도 통과했습니다. 다만 이관 뒤 과거 회차가 다시 들어올 때의 차단 조건이 빠졌습니다.

  • 제공자 I는 불확실한 전송 뒤 조회만 하고, N은 운영자 판단을 기다리도록 했습니다.
  • 소유권 / 취소 / 영수증 관련 자체 SQL 검사를 재실행해 통과했습니다. 삭제된 임시 검사 파일은 실행 기록에서 원문을 복구해 보존했습니다.
  • 별도 검사에서는 11월 22일 이관 뒤 다시 들어온 11월 20일 회차가 발송 직전 상태까지 갔습니다. 도구 재매핑 인가만 있었고, 과거 회차의 재실행 인가는 없었습니다.
  • future_only 표시는 저장하지만 등록 SQL이 처리 경계를 검사하지 않습니다. 재입력이 가능한 조건에서는 영속적인 신규 처리 하한이나 동등한 차단 절차가 필요합니다.
  • 실제 외부 전송은 하지 않았습니다. 이 초안의 이관 경계 문제이지, 모델이 설계를 수정할 수 없다는 판정은 아닙니다.
AGY / Gemini Flash — gemini-3.8-flash-medium / medium

불확실성과 외부 펜싱 한계는 짚었지만, 안전 보장과 SQL 사이에 수정이 필요한 부분이 있었습니다.

  • 20시간 안의 재전송을 안전한 기본값으로 삼았지만, 도착 지연이 무제한이면 그 시간 제한으로 중복을 막지 못합니다. 자기 검토에서도 남은 위험을 언급해 설명이 충돌합니다.
  • 등록 SQL의 ON CONFLICT 조건이 부분 유일 인덱스와 맞지 않는 오류를 실제 SQLite에서 재현했습니다.
  • 새 소유권이 생긴 뒤 오래된 워커의 occurrence 갱신은 막혔습니다. 반면 request_intents의 상태 갱신은 허용됐습니다. 두 결과를 구분했습니다.
  • 과거 revision 내용 보존, 취소 후 결과 기록, 시계와 이관 절차도 추가 검토가 필요합니다.
  • 이 초안의 결함이지, 모델이 수정할 수 없다는 판정은 아닙니다.
실제로 확인한 결함과 시험 범위

AGY 초안의 등록 SQL은 부분 유일 인덱스와 ON CONFLICT 조건이 맞지 않아 SQLite에서 오류가 났습니다. 오래된 워커의 occurrence 갱신은 막혔지만, 같은 워커가 request_intents의 상태를 바꾸는 쓰기는 허용됐습니다. 둘을 구분해 기록했습니다.

키 만료 문제는 다음 순서로 드러납니다. 원본 요청은 0시간에 보냈지만 26시간에 도착합니다. 0.5시간의 키 조회에는 아직 결과가 없습니다. 1시간에 보낸 재시도가 먼저 수락되면 키는 25시간에 만료됩니다. 이후 원본이 도착하면 두 번째 효과가 생깁니다. 클라이언트 기준 12시간이나 20시간 제한만으로는 중복 금지를 보장하지 못합니다.

Sol과 Astra는 불확실한 POST를 반복하지 않는 설계를 냈습니다. 이 경우 중복을 줄이는 대신 실제로 전송하지 못한 건도 미확정 상태에 남을 수 있습니다. Opus는 12시간 내 재시도를 택하고 이 중복 위험을 명시했습니다. 엄격한 중복 금지가 필요하면 Opus안의 기본 정책을 바꿔야 합니다.

검토 에이전트가 DDL을 임시 메모리 DB에 읽고, 일부 상태 전이를 실행했습니다. Sol의 별도 SQL 프로브, Astra의 전이 검사 재실행, Opus가 제공한 메모리 DB 검사 재실행은 통과했습니다. 각 후보의 자체 검사 개수는 다르므로 많고 적음으로 순위를 매기지 않았습니다. 실제 프로세스 강제 종료, 제공자 서버, WAL 부하와 운영 이관을 검증한 것은 아닙니다.

설계 원본과 실행 로그는 별도로 보존했습니다. 기존 업무분장은 자동으로 바꾸지 않았습니다. 작은 코드 / 웹 UI 시험과 이 설계 과제의 결론도 구분합니다.

  • 16 / 16같은 공통 CDP 도구로 입력, 클릭, 결과와 캡처 확인.
  • 같은 대화 유지후속 턴에서 앞서 고친 버그를 기억하고 문서 조사와 UI 시험을 이어갔습니다.
문서 조사와 공통 스킬▾

지정한 공식 문서 두 개를 읽고 AGY의 Google 로그인과 OpenClaw의 Gemini API 키 연결을 구분했습니다. 공통 스킬도 직접 읽고 본문 확인 문구와 SHA256을 기록했습니다.

이번에는 공통 스킬 v02를 명시적으로 읽었습니다. 최초 네 조합은 v01을 읽었으므로, 이 항목까지 완전히 같은 조건은 아닙니다. 스킬 목록에서 자동으로 발견한 결과로 해석하지 않습니다.

브라우저 연결과 시험 범위▾

내장 브라우저 도구는 “The browser access host is unavailable” 오류로 조작하지 못했습니다. 이후 기존 시험과 바이트가 같은 공통 CDP 도구를 새 Chrome 프로필에 연결해 성공했습니다. macOS 화면 조작은 시험하지 않았습니다.

코드의 경계 조건과 작은 웹 양식을 확인한 결과입니다. 어려운 구조 설계, 대규모 작업, 속도, 비용의 우열은 측정하지 않았습니다. 담당 배정은 바꾸지 않습니다.
